# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase nature:** Two independent-but-jointly-tested capabilities layered onto the existing, locked light-theme/moderate-motion foundation (`01-UI-SPEC.md`) and component conventions (`03-UI-SPEC.md`): (1) a scroll-reactive visual state for the existing fixed header (HEAD-01/02), and (2) a new equipment showcase carousel (EQUIP-01). Neither redefines color, motion timing, spacing scale, or typography weights — both only *apply* Phase 1's locked tokens. **No interactive channel was available to pause mid-research for the open design questions this phase raises** (carousel layout/placement, header threshold) — consistent with Phase 1's precedent, each is resolved below with documented rationale under "Discretion Calls," sourced directly from codebase inspection, `PITFALLS.md`, and the locked Phase 1/3 contracts. Flag any of these for user correction before/during planning if they don't match intent.

**Two codebase facts that change how HEAD-01/02 must be read (verified this session, not assumptions):**
1. `.site-header` is currently `position: fixed`, **not** `position: sticky` (`app/globals.css` line 21). REQUIREMENTS.md/ROADMAP.md's "header sticky"/"position: sticky" wording is the colloquial sense (a header that stays stuck to the top), not the literal CSS property. **Do not introduce a literal `position: sticky` declaration on `.site-header` this phase** — doing so would be an unrequested architecture change and would newly expose the header to the exact `overflow-x`/containing-block class of bug PITFALLS.md Pitfall 5/8 describes for `position: sticky` elements, which `position: fixed` is not equally vulnerable to. Keep `position: fixed`; add only the scroll-reactive class toggle.
2. Lenis is already configured with `root` mode (`components/providers/smooth-scroll-provider.tsx`: `<ReactLenis root options={{...}}>`) — this is exactly the "native-scroll-friendly mode" STATE.md's Blockers section flagged as needing verification against `lenis@1.3.25`. **Already satisfied; not an open risk for this phase.** `window.scrollY` and native scroll-dependent CSS read the real scroll position.

The codebase's one actual `position: sticky` consumer is `.tech-sticky` (Technology section's pinned parallax block, `app/globals.css` line 35) — **this**, not the header, is the literal sticky element HEAD-02's stress test must include. `body{overflow-x:hidden}` already exists in `app/globals.css` (line 13, pre-dates this phase) — do not add any *further* `overflow-x` rule anywhere; if the carousel's slide track needs horizontal-overflow containment, scope `overflow-x: clip` to the carousel's own wrapper only, never to `html`/`body`.

## Header Scroll-Reactive Contract (HEAD-01, HEAD-02)

| State | Visual treatment |
|-------|-------------------|
| Default (scrollY ≤ 80px) | Unchanged from Phase 1–3: `background: transparent`, no shadow, `color: var(--ink-primary)` |
| `.site-header.is-scrolled` (scrollY > 80px) | `background: var(--bg-surface)` (`#FFFFFF`); `box-shadow: 0 1px 0 var(--border-subtle), 0 8px 24px color-mix(in srgb, var(--ink-primary) 6%, transparent)` — a single subtle hairline + soft ambient shadow, not a heavy drop-shadow (per PITFALLS.md's UX-pitfall table: a header that visibly animates/changes aggressively on every scroll pixel reads as busy on a "sober, technical" site) |

**Threshold:** a single discrete value, **80px** (roughly one header-height of scroll — header is ≈70–75px tall from its existing `1.35rem` vertical padding) — not a percentage-of-viewport or per-section value. Chosen so the toggle fires almost immediately on any deliberate scroll, giving clear feedback without a large "dead zone" at the top.

**Implementation contract (verbatim from `01-UI-SPEC.md`'s own pre-guidance for this component, restated here as the concrete instance):**
```
ScrollTrigger.create({
  start: "80px top",           // or the equivalent trigger against document.body — exact syntax to be verified against the installed gsap@3.15.0/ScrollTrigger API during planning
  toggleClass: { targets: ".site-header", className: "is-scrolled" },
})
```
- Registered inside the existing single ticker/`useGSAP()` scaffolding (`lib/gsap.ts` / `smooth-scroll-provider.tsx`) — **no second `window.addEventListener("scroll")`**, per HEAD-01's explicit hard constraint.
- **No continuous/scrubbed interpolation** — this is a binary class toggle only (`toggleClass`, not `scrub`), consistent with Phase 1's Motion Contract ("no `scrub`-driven continuous timelines... must be a discrete threshold toggle").
- Transition on the toggle itself: `background var(--motion-duration-fast) var(--ease-moderate), box-shadow var(--motion-duration-fast) var(--ease-moderate)` (200ms) — fast enough to feel responsive, short enough to stay in the "micro-interaction" tier per Phase 1's own duration-token usage guidance (`--motion-duration-fast` is reserved for exactly this: "Hover/focus micro-interactions").
- Header height/padding does **not** change on scroll (no grow/shrink) — background/shadow only, per Phase 1's explicit locked guidance for this exact component.

**HEAD-02 verification checklist (must be performed manually, not just visually spot-checked — restated from ROADMAP.md's own literal success criteria plus PITFALLS.md Pitfall 8's specific test list):**
1. Fast flick-scroll past the 80px threshold and back — header toggles cleanly, no flicker/lag.
2. `.site-header.is-scrolled` state persists correctly with the Phase 3 service drawer open AND closed (drawer's `useScrollLock`/`lenis.stop()` must not desync the header's `ScrollTrigger`).
3. `.tech-sticky` (the codebase's actual `position: sticky` element) still pins/releases correctly with the carousel present directly below it in the same section, and with the header's new class toggle active.
4. No new `overflow-x` rule was introduced anywhere in `app/globals.css` as a side-effect of adding the carousel (grep confirms `overflow-x` still appears only on `body`, its pre-existing single occurrence).
5. Menu overlay open/closed does not desync the header's scroll-based class (menu-open freezes scroll via `useScrollLock`, so `.is-scrolled` should simply hold whatever state it was in when the menu opened — this is expected, not a bug).

## Equipment Carousel Contract (EQUIP-01)

### Placement (Discretion Call 1 — see rationale below)

The carousel is a **sub-block appended inside the existing `TechnologySection` component** (`components/sections/technology-section.tsx`), rendered after `.tech-sticky` and before the section's closing tag — **not** a new standalone numbered section. It inherits `.technology`'s existing `--bg-surface` (white) background; no new section-level background declaration is needed. It does **not** get a new `.section-kicker` with a `01–05` number (see Typography above) and does **not** get a new `menu-overlay.tsx` nav entry — both would ripple into renumbering the four other locked section kickers and are out of scope for a phase whose own ROADMAP goal is "header + carousel," not a new page section.

### Structure

```
<div className="equipment-showcase" data-reveal>
  <div className="site-shell">
    <span className="mono-label">Equipo en campo</span>
    <h3>Instrumentos que usamos en cada levantamiento.</h3>
    <p>...one-sentence intro...</p>
  </div>
  <div className="embla" aria-roledescription="carousel" aria-label="Equipo técnico">
    <div className="embla__viewport" ref={emblaRef}>
      <div className="embla__container" data-lenis-prevent>
        <div className="embla__slide" role="group" aria-roledescription="slide" aria-label="1 de 2">
          <div className="media-frame embla__frame"><Image .../></div>
          <p className="tech-caption">...</p>
        </div>
        <!-- slide 2, aria-label="2 de 2" -->
      </div>
    </div>
    <button className="circle-link embla__prev" aria-label="Equipo anterior">←</button>
    <button className="circle-link embla__next" aria-label="Equipo siguiente">→</button>
    <div className="embla__dots" role="tablist" aria-label="Seleccionar equipo">
      <!-- 2 button dots, aria-selected -->
    </div>
    <p className="sr-only" aria-live="polite">Equipo {n} de 2</p>
  </div>
</div>
```

### Slide sizing (locked, breakpoints reuse Phase 3's exact 720px/1000px thresholds for consistency)

| Breakpoint | Slide width (`flex-basis`) | Gap | Effect |
|---|---|---|---|
| Desktop (>1000px) | `58%` | `24px` (lg token) | Slide 1 nearly fills the viewport; slide 2 visibly peeks in at the right edge (~30–35% visible) — genuine navigation is required to see it fully, but its existence is immediately obvious, satisfying PITFALLS.md's UX-pitfall guidance ("show a partial peek of the next slide... so the carousel's extent is discoverable") even with only 2 total slides |
| Tablet (721–1000px) | `72%` | `16px` (md token) | Same peek principle, narrower margin |
| Mobile (≤720px) | `84%` | `16px` (md token) | Standard mobile single-card-with-peek convention |

**Why not show both slides fully side-by-side (a "2-up" layout) instead:** rejected — with only 2 slides, a layout where both fit entirely on screen at once leaves nothing to navigate, which would make EQUIP-01's keyboard/touch navigation requirement untestable/meaningless. The peek layout keeps real navigation functional now and requires zero redesign once more equipment photos are added later (per the phase brief's explicit "more to be added later" note).

**Slide frame:** reuses the existing `.media-frame` class verbatim (thin `--border-subtle` overlay border, `1.2s` hover image-scale — already declared in `app/globals.css`, no new declaration needed) at `aspect-ratio: 4/5` (matches both source images' actual proportions: `equipos1.png` 685×835 ≈0.82, `dron.png` 675×782 ≈0.86 — `4/5`=0.8 is the closest clean ratio, `object-fit: cover` handles the small remaining crop), background `--bg-surface-deep` for the letterbox/load-in fill.

**Caption:** below the image (not overlaid on the photo — avoids the exact "contrast on a photo background" re-check PITFALLS.md's performance-traps table flags), reusing `.tech-caption`'s existing 0.68rem/500/uppercase styling verbatim.

### Navigation controls (keyboard/touch parity — EQUIP-01, PITFALLS.md Pitfall 6)

- **Prev/Next buttons:** always visible, 44×44px circles, reusing `.circle-link`'s exact existing visual treatment (border `--border-strong`, hover → `--accent` fill + white icon + `rotate(-8deg)`, `:focus-visible` → `outline: 2px solid var(--focus-ring); outline-offset: 2px`). Disabled state (start/end of track, since `loop: false`) reuses the site's existing disabled convention: `opacity: .4; cursor: not-allowed; pointer-events: none`.
- **Keyboard:** buttons are real `<button>` elements (Enter/Space activate them natively); additionally, the carousel viewport itself is focusable and responds to `ArrowLeft`/`ArrowRight` per the ARIA APG carousel pattern.
- **Touch/swipe:** native Embla drag — `data-lenis-prevent` on `.embla__container` so Lenis's own touch-smoothing does not fight the carousel's drag gesture (per PITFALLS.md UX-pitfall table and EQUIP-01's own explicit requirement).
- **Dots:** 2 small (8px) `role="tablist"`/`role="tab"` buttons — inactive: `border: 1px solid var(--border-subtle)`, transparent fill; active: `background: var(--accent)`, no border. Each has `aria-label="Ir al equipo N"` and `aria-selected`.
- **No auto-advance** (locked, EQUIP-01) — so WCAG 2.2.2 (Pause/Stop/Hide) does not apply; no pause control is needed or should be built.
- **Reduced motion:** Embla's `scrollTo()` transition (triggered by prev/next click or dot click) is gated through the same `prefers-reduced-motion` check already established in `lib/motion-preferences.ts` — reduce to an instant jump instead of an eased scroll when active. Drag-gesture physics (user-initiated, not decorative) are left as Embla's default regardless of the reduced-motion setting, consistent with how a native scrollable list is not itself required to disable user-driven gestures.
- **No custom GSAP slide-transition** is introduced beyond Embla's own drag/`scrollTo()` handling (per `SUMMARY.md`/PITFALLS.md Pitfall 7 — a headless library's own transition is the single animation authority here; there is nothing else to drive through the GSAP ticker for this simple 2-slide case).

### Content note (flagged, not a Phase 4 blocker)

`dron.png` is already used as `TechnologySection`'s pinned hero image (`.tech-media`, directly above this carousel in the same section) with the caption "Matrice 350 RTK / Plataforma aérea." Reusing it as a carousel slide directly below means the same photo appears twice in quick succession on the page. This is **accepted per the user's 2026-07-20 confirmed decision** to proceed with only the 2 currently-available images — flag for a content follow-up (swap in a distinct photo, or move the carousel further from the Technology hero) once real equipment photography is supplied, but do not block Phase 4 on it.

No new timing values — this phase consumes Phase 1's locked "moderate motion" spec verbatim (`--motion-duration-fast`/`--ease-moderate` for the header toggle; Embla's own drag physics for the carousel, per the explicit "do not introduce a competing GSAP transition" guidance above).

| Interaction | Timing | Notes |
|---|---|---|
| `.site-header.is-scrolled` background/shadow toggle | `var(--motion-duration-fast)` (200ms), `var(--ease-moderate)` | Binary class toggle only, no scrub — see Header contract above |

## Discretion Calls (no interactive channel available — documented rationale, flag for correction if wrong)

1. **Carousel placement: sub-block inside `TechnologySection`, not a new standalone numbered section.** The site's 5 numbered section kickers (`01` Perspectiva → `05` Contacto, verified against every section component this session) are fully allocated; inserting a 6th numbered section would require renumbering at least Proceso/Contacto and adding a new `menu-overlay.tsx` nav entry — neither is requested by ROADMAP.md's Phase 4 goal ("header reactivo... y carrusel... probados juntos"), which scopes this phase to exactly two additions, not a page-structure change. Placing the carousel as a themed continuation of the existing Tecnología section (which already covers drones/instruments) also directly reuses that section's white `--bg-surface` background without disturbing the locked "gris arriba, blanco abajo" alternation sequence from `01-UI-SPEC.md`.
2. **Header scroll threshold set to a fixed 80px, not a percentage or per-section value.** ROADMAP/REQUIREMENTS specify only the toggle mechanism (`ScrollTrigger.create({toggleClass})`), not a numeric threshold. 80px ≈ one header-height of scroll is a standard, low-friction default for this exact pattern (background/shadow appears almost as soon as the user starts scrolling, avoiding a large "nothing happens" dead zone at the top) and keeps the toggle a single hard-coded constant the planner can adjust in one place if it feels early/late in review.
3. **Carousel slide peek ratio (58%/72%/84% desktop/tablet/mobile) chosen over a full 2-up layout.** See "Why not show both slides fully side-by-side" under Equipment Carousel Contract above — a 2-up layout would make EQUIP-01's navigation requirement untestable with only 2 slides.
4. **`dron.png` reused despite already appearing in the same section's hero.** No third equipment image exists; the user's 2026-07-20 decision to proceed with 2 images is already locked and not re-litigated here — this is flagged as a content follow-up, not a phase-4 blocker.
