# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase nature:** This is a foundational/architectural phase (unified Lenis+GSAP engine, reduced-motion gate, component decomposition, `FormConnector` removal, legacy v4 deletion). It introduces **zero new visible UI**. This UI-SPEC has two jobs:
1. Lock down the **motion/interaction contract** that Phases 2–5 will build on (scroll feel, reduced-motion behavior, timing/easing tokens).
2. Lock down a **visual regression contract**: nothing in this phase may change what the site looks like today.

This is a pre-existing, deliberate editorial-layout convention, not a defect, and Phase 1 does not modify it.

| Token | Value | Usage |
|-------|-------|-------|
| — | — | Not applicable this phase — carried over verbatim from `app/globals.css`. No new spacing decisions are made in Phase 1 (no new visible UI). |

Exceptions: none. If a later phase needs a genuinely new spacing scale (e.g. for a new UI element not present today), it must be defined in that phase's own UI-SPEC, not retrofitted here.

Additional weights present in the existing system beyond the template's 2-weight guideline (documented for accuracy, not introduced by this phase): 600 (brand mark, CTA/submit-button labels), 650 (brand wordmark), 700 (submit button), 480 (statement/perspectiva copy), 400-italic (accent title line, `em` color accent). ## Motion & Interaction Contract

This is the primary deliverable of this phase's UI-SPEC. It establishes the shared scroll/motion foundation that every subsequent phase (2–5) must build on rather than re-deciding.

### Scroll Engine (locked)

- Single frame loop: Lenis driven entirely by GSAP's ticker — no competing `requestAnimationFrame` loops (directly satisfies FOUND-01, avoids Pitfall 4).
- Lenis options (normal/no-preference state): `autoRaf: false`, **`lerp: 0.07`** (cinematic/heavier feel — locked by user, deliberately more viscous than the 0.1 "moderate" default), `syncTouch: true`.
- Sync wiring: `gsap.ticker.add((time) => lenis.raf(time * 1000))`, `gsap.ticker.lagSmoothing(0)`, `lenis.on('scroll', ScrollTrigger.update)`.
- Plugin registration: once, module scope, in `lib/gsap.ts` — never inside a component body or `useEffect` (Anti-Pattern 4 / Pitfall 1).
- Provider: single `SmoothScrollProvider` client component wrapping `{children}` in `app/layout.tsx`, per `.planning/research/ARCHITECTURE.md` Pattern 1.

### Reduced-Motion Contract — "Softened, not binary off" (locked)

**This is an explicit, deliberate interpretation lock.** When `prefers-reduced-motion: reduce` is active:

- **Lenis is still instantiated** — it is NOT skipped/fallen-back-to-native-scroll. Its `lerp` is raised to **`0.15`** (snappier, less inertia than the normal `0.07`, but still smoothed — not a hard cut to native scroll).
- **GSAP timelines still play** — they are NOT set to instant end-state (`gsap.set`) and are NOT skipped. Instead, under the `reduceMotion` branch of `gsap.matchMedia()`:
  - Duration is scaled to **~50% of normal** (e.g. a 0.9s reveal becomes ~0.45s).
  - Translation/movement distances are scaled to **~25–35% of normal** (e.g. a 44px slide-up becomes ~12–16px).
  - Easing is simplified to non-elastic, non-overshoot curves (e.g. `power1.out` instead of pronounced back/expo eases).
  - Pinning/scrub-heavy effects (mask transitions, scroll-scrubbed timelines — Phase 3/4 concern) shorten pin duration/scrub range rather than being skipped entirely.
- This softened contract is established once, in Phase 1's `gsap.matchMedia()` scaffolding (`lib/motion-preferences.ts`, per `.planning/research/ARCHITECTURE.md` Pattern 3), as the shared reduced-motion branch signature every later phase's animation must reuse — not reinvent.

**⚠️ Flag for `/gsd-plan-phase`:** `ROADMAP.md`'s Phase 1 success criterion #3 currently reads *"...stops GSAP timelines from animating"* — a binary-off interpretation. This UI-SPEC locks the opposite: reduced-motion users still see (shorter, subtler) animation, per explicit user decision during this UI-SPEC session. **The plan's acceptance test for FOUND-02 should verify "animations play but are measurably shorter/subtler and Lenis is snappier under reduced motion," not "zero animation fires."** Flag this discrepancy to the user/planner before writing FOUND-02's task-level acceptance criteria so the plan doesn't silently contradict this contract.

### Easing & Duration Tokens (reference for Phase 2+, carried over from existing CSS — not re-decided)

| Token | Value | Existing usage in `app/globals.css` |
|-------|-------|----------------------------------------|
| `ease-reveal` | `cubic-bezier(.16,1,.3,1)` | `[data-reveal]` fade/slide, `.media-frame` hover scale, `.service-row:before` wipe, `.process-step i` underline |
| `ease-sharp` | `cubic-bezier(.76,0,.24,1)` | `.intro:after` wipe, `.menu-overlay` clip-path open/close |
| `duration-fast` | 0.3–0.35s | Hover states, form input focus border transition |
| `duration-base` | 0.55–0.9s | Reveal fade/slide, media hover scale |
| `duration-slow` | 1.15–1.2s | `.title-line[data-reveal]>span` stagger reveal, intro progress bar, menu overlay clip-path open |

**Note for Phase 2+ implementers:** GSAP tweens do not accept raw CSS `cubic-bezier()` syntax directly. When these tokens are consumed by new GSAP timelines, either register them via `CustomEase.create()` (free GSAP plugin, same control points) or approximate with named GSAP eases (`power3.out` approximates `ease-reveal`; `power4.inOut`/`expo.inOut` approximates `ease-sharp`). Phase 1 does not need to implement this itself — it only locks the token values so Phase 2 doesn't invent new curves that drift from the site's existing motion language.

### Component Decomposition Contract (ARCH-02)

Each of the following becomes its own `"use client"` component with its own `useGSAP({ scope })` call, replacing the monolithic `components/experience.tsx`, with **zero markup/visual change** during the split: `HeroSection`, `ManifestoSection` (perspectiva/statement), `CapabilitiesSection`, `TechnologySection`, `ProcessSection`, `ContactSection` (renders `ContactForm`), `MenuOverlay`, `Cursor`. See `.planning/research/ARCHITECTURE.md` for the full recommended file structure.

### Visual Regression Contract (explicit "no visible change" gate)

- **Zero change permitted** to: colors, fonts, spacing, copy, layout, breakpoints, or any existing CSS class/selector in `app/globals.css` as a result of this phase's work.
- Verification: manual visual comparison at 1440×900 and 390×844 before/after the `experience.tsx` decomposition (this codebase has no automated visual-regression tooling per `.planning/codebase/CONCERNS.md` — this is a manual QA checklist item for the executor, not an automated gate).
- `ContactForm` extraction (ARCH-01) must not change the form's rendered markup, classes, or field order — only how the submit handler is wired (component-owned `onSubmit`, no `document.querySelector`).
- Deleting `landing-page-v4.html`, `lib/v4-template.ts`, `components/v4-interactions.tsx` (ARCH-03) must have zero effect on the live site — confirm none of these files are imported/referenced anywhere in `app/` or `components/` before deletion.
